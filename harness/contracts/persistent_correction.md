# persistent-correction

**Type:** Post-check (code-enforced, Haiku-judged)
**Failure mode:** FM-033 (recurrence of corrected behavior)
**Trigger:** Every response, after a correction has been logged

**Precondition:** Response must not reproduce a behavior that the user corrected in a prior turn or session.

**Enforcement:** `core/contracts.py:PersistentCorrectionContract.check_post()` — Haiku evaluates the response against recent correction entries. Blocks if the corrected pattern recurs.

**Home-proxy proximity gate:** auth keywords (twitter/gmail/upwork/oauth) only flag a handoff when colocated within 150 chars (same sentence) of a true delegation signal — 1st-person inability ("I can't / cannot / am unable to") or 2nd-person delegation ("need you to", "you'll need to", "requires you", "from your desktop", "not possible from here", "no access from here"). Status phrases like "blocked by X" or "this is blocked" no longer trigger — they describe loop state, not a the user-handoff. Tightened 2026-06-11 after 124/24h false-positive fires from status digests.

**Load-time filters in `_load_stops()`** (defense-in-depth against bad miner output):
- `_is_source_redirect()` — drops "switch to X / find Y instead" directives that are content corrections, not behavioral stops (2026-06-12).
- `_contradicts_claude_rule()` — drops directives that contradict load-bearing CLAUDE.md rules. E.g. "Stop trying to find workarounds for blockers" (mined 2026-04-27 from the user's rhetorical "Can you not find a way past it?") directly contradicts CLAUDE.md rule #13 (try home proxy before surfacing blockers). Filter list lives in `_CONTRADICTS_CLAUDE_RULES`. Added 2026-06-13 after the directive resurfaced as a persistent-correction fire. Extended 2026-06-14 to also drop "Don't perform unsolicited checks or verification steps — only do what was asked" (mined 2026-05-19), which contradicts CLAUDE.md rules #3 (verification cite required), #14 (Revenue $ claims require Stripe read), #22 (auto-confirm receipts on completed ops), and #29 (commit hash from `git rev-parse HEAD`). Extended again 2026-06-14 (gap-closer) to drop "Don't wire it to home proxy" variants, which contradict CLAUDE.md rule #13. Fired 2x in the 4h gap-closer window before the filter was extended. **Extended once more 2026-06-14b** (gap-closer follow-up) to drop **"Use the home proxy/WireGuard route…"** — an inverted-intent mine where the miner converted the user's *positive* instruction "We've done this through home proxy. Figure it out" into a *stop* directive on home-proxy use. That directly contradicts CLAUDE.md rule #13. Fired twice in the 4h gap-closer window (15:51, 16:30) — load-time filter now drops it permanently. **Extended 2026-06-15** (gap-closer) to drop **"Stop showing daily Claude cost"** — the user's original message ("Can you fix this Claude usage calc. It's just wrong. Also can you do month to date of Claude rather than day?") was a switch-to-MTD request, not a categorical stop on Claude-cost content. `scripts/daily_summary.py` now reports `Claude MTD (month):` correctly, so the intent is implemented at the data layer. Haiku still mis-judges any response mentioning Claude usage/cost as repeating the stop, producing 2 FP fires in the 4h gap-closer window (23:26, 23:29 on dev sessions touching `scripts/claude_usage_tracker.py`). Load-time filter now drops it. **Extended again 2026-06-15b** (gap-closer follow-up) to drop two inverted-mine *positive* directives: **"Replace any 'worth a look'… with immediate execution"** and **"When asked a direct question, answer it immediately…"**. Both were mined as stops but actually encode positive instructions that already live in CLAUDE.md (default-to-action, direct answers). The stop-form regenerates a fire every time the response contains the trigger phrase. Together they accounted for 4/26 persistent-correction fires in the 24h window (and 2/5 in the 4h gap-closer window). Filter list now drops them.

**Cache invalidation:** `_stops_cache` was historically keyed only on the stops file mtime, which meant a code-side filter list change (`_CONTRADICTS_CLAUDE_RULES`) would NOT take effect on a running bot until the file was touched. That was the proximate cause of the 2026-06-14 stale-cache fires (filter shipped but old stops were still active). Gap-closer 2026-06-14: cache key now also includes the filter list itself (`_stops_filter_key`), so code-side changes invalidate the cache immediately on next read. Locked in by `test_filter_list_change_invalidates_cache`.

**Recovery:** Read the correction. Apply the fix permanently. Do not reproduce the corrected behavior.

**Escalation:** Surface to the user only if the pattern requires an architectural change to prevent.
